# Zuluhotel Omega 3 - In-Game Regression Test Plan (v3.0.3)

## Purpose
This test plan validates the gameplay and script changes implemented during the ZH2.5 -> ZH3 parity/fix pass.

## Scope Covered
- Class behavior and restrictions (all classes touched in this cycle)
- Physical combat pipeline changes
- Astral/spell damage pipeline changes
- Slayer behavior restoration
- Elemental weapon behavior restoration
- Missing hitscript restoration (`:combat:critstaminahit`)
- Party-safe AoE and pet/master safety
- No-PK area safety behavior
- Spell targeting and cast validation behavior

## Test Environment Setup
1. Use at least 3 player characters:
- `P1` = primary tester (caster/attacker)
- `P2` = friendly party member
- `P3` = non-party player
2. Prepare at least 4 NPC types:
- Tamed pet of `P1`
- Tamed pet of `P2`
- Unrelated hostile NPC
- Summoned/animated/charmed NPC if available
3. Prepare map locations:
- Normal PvP-enabled area
- No-PK area
- Safe area
4. Enable visible feedback:
- Use in-game feedback messages (system messages / overhead text)
- Capture console `Print()` output where available
- Always review `log/pol.log` and syslog after each test block

## Pass Criteria
- All expected outcomes occur exactly as listed.
- No script errors in logs.
- No missing hitscript/runtime lookup errors.
- No unexpected friendly-fire in protected scenarios.

## Section A - Critical Runtime Sanity

### A-01 Missing hitscript check (`critstaminahit`)
Steps:
1. Equip a weapon that uses `Hitscript :combat:critstaminahit`.
2. Hit valid targets repeatedly (player and NPC).
Expected:
- Weapon attacks execute normally.
- No "script not found" / missing hitscript error in log.
- Crit + stamina-drain behavior can trigger without runtime failure.

### A-02 General combat script load sanity
Steps:
1. Use normal weapon (`mainhit`), slayer weapon (`slayerscript`), and spell-on-hit weapon (`spellstrikescript`).
2. Hit both NPC and player targets.
Expected:
- All hit types resolve damage.
- No script include/runtime errors.

## Section B - Class Restrictions and Class Combat Touchpoints

### B-01 Class restriction enforcement baseline
Classes to verify:
- Mage, Paladin, Ranger, Thief, Warrior, Bard, Bladesinger, Crafter, Mystic Archer, Powerplayer
Steps:
1. For each class, equip a legal weapon/armor set.
2. Attempt to equip known restricted item graphic.
3. Attempt to equip known restricted objtype item.
Expected:
- Legal items equip normally.
- Restricted items are blocked consistently per class rules.

### B-02 Crafter class-specific checks
Steps:
1. Verify Crafter recognized as Crafter by class displays/behavior.
2. Verify Crafter max circle gate is enforced at intended value.
3. Equip/unequip items with skill advancement properties including magery-adv variants.
Expected:
- Crafter class identity is stable.
- Circle cap is applied as configured.
- Crafter-specific skill-enchant restriction exceptions behave correctly.

### B-03 Powerplayer holybook scaling checks
Steps:
1. Cast `enlightenment` as Mage, Paladin, Powerplayer, and non-listed class.
2. Cast `seraphims will` as Mage, Paladin, Powerplayer, and non-listed class.
Expected:
- Powerplayer receives explicit class branch behavior (not generic fallback).
- Scaling differences between classes match intended branch logic.

### C-01 Slayer multiplier in core physical pipeline
Steps:
1. Use slayer-type weapons against matching and non-matching NPC types.
2. Test Human slayer against player target.
Expected:
- Matching creature type applies slayer bonus.
- Non-matching type does not apply slayer bonus.
- Human slayer applies expected player-target behavior (ZH2.5 parity).

### C-02 Slayer + alternate hitscripts
Steps:
1. Use slay-type weapons that hit through `mainhit`, `slayerscript`, and `spellstrikescript` (if configured).
Expected:
- Slayer behavior still applies through restored core handling where intended.
- No double-application artifacts.

### C-03 Critical + stamina drain hitscript behavior
Steps:
1. Attack repeatedly with `critstaminahit` weapon.
2. Track target stamina and attacker stamina before/after triggers.
Expected:
- Critical strike chance behavior occurs.
- Stamina drain/transfer occurs on trigger.
- No negative stamina or overflow edge issues.

## Section E - Spell Targeting and Cast Validation

### E-01 Area target safe-zone validation
Steps:
1. Attempt area-target casts in safe area.
2. Attempt same casts in normal zone.
Expected:
- Safe area cast attempts are blocked with proper feedback.
- Normal area casts proceed.

### E-02 Target rejection handling
Steps:
1. Trigger conditions that set target rejection (invalid/denied target flow).
2. Attempt cast again immediately.
Expected:

## Section F - Party, AoE, and Pet/Master Safety (Highest Priority)

### F-01 Master should not damage own pet with AoE
Steps:
1. `P1` summons/tames pet.
2. `P1` casts AoE hitting area including pet.
Expected:
- Own pet excluded from damage.

### F-02 Master should not be damaged by own pet-origin effects
Steps:
1. Trigger pet-origin effect around master (where applicable).
Expected:
- Master-safe behavior is preserved.

### F-03 Party member should not be hit by AoE/casting clothes procs
Steps:
1. `P1` and `P2` join same party.
2. `P1` triggers AoE and casting-clothes proc near `P2`.
Expected:
- `P2` is excluded from harmful hit list.

### F-04 Party member pets should not be hit
Steps:
1. `P2` has tamed pet nearby.
2. `P1` triggers AoE/casting procs covering pet.
Expected:
- Party member pet excluded from harmful effects.

### F-05 Non-party player in No-PK should not be hit
Steps:
1. Place `P3` (not in party) in No-PK area.
2. Attempt harmful AoE/casting from `P1`.
Expected:
- `P3` not damaged.

### F-06 Non-party pets/master links in No-PK should not be hit
Steps:
1. Place `P3` and `P3` pet in No-PK area.
2. Trigger harmful AoE/casting around both.
Expected:
- Both protected by No-PK filtering where intended.

### F-07 Mixed party + non-party + pets stress test
Steps:
1. In one cast radius include: `P1`, `P2`, `P2 pet`, `P3`, `P3 pet`, hostile NPC.
2. Trigger several AoE variants (spell, song, item proc).
Expected:
- Friendly and party-linked entities filtered out.
- Valid hostile/non-protected targets are hit.
- No skipped/incorrect victims due to list mutation issues.
